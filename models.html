Les modèles proposés par AstroGraphAnomaly

AstroGraphAnomaly ne cherche pas à “prouver” qu’un objet est exceptionnel. Il construit un graphe à partir des sources, extrait des indicateurs astronomiques et structurels, puis propose plusieurs moteurs de scoring pour repérer les candidats qui méritent une vérification humaine.

Le chemin de lecture

La logique du dépôt est simple : transformer un catalogue en graphe, enrichir les nœuds, scorer les sources, puis produire des fichiers lisibles et vérifiables.

1. DonnéesCSV local, Gaia DR3 via requête, ou CSV de type Hubble/HST.
2. GrapheConstruction d’un graphe k-NN sur RA/Dec, coordonnées 3D ou fallback PCA numérique.
3. FeaturesAttributs astro + métriques de graphe : degré, clustering, k-core, communautés, ponts.
4. ModèleScoring par Isolation Forest, LOF, One-Class SVM, Robust Z-Score, PineForest ou ensemble.
5. RapportCSV, GraphML, PNG, LIME, prompts LLM, manifest et rapport HTML autonome.

Modèles / moteurs disponibles

Dans le code, ils sont appelés engine. Le mot “modèle” est donc à comprendre comme moteur de scoring d’anomalie, pas comme preuve astrophysique finale.

Point de départisolation_forest

Isolation Forest

Isole les points rares via des arbres aléatoires. Rapide, robuste et très utile pour une première passe sur un catalogue.

Utile pour
  • repérer des extrêmes multivariés
  • faire un tri rapide sur beaucoup de sources
  • obtenir une base de comparaison stable
Limite
  • dépend du paramètre contamination
  • ne comprend pas le sens astrophysique des anomalies
Densité localelof

Local Outlier Factor

Compare une source à son voisinage local. Très intéressant quand les données contiennent plusieurs régions ou populations différentes.

Utile pour
  • détecter ce qui est étrange localement
  • éviter qu’un seul nuage global écrase les sous-structures
  • compléter Isolation Forest
Limite
  • sensible au nombre de voisins
  • moins confortable sur très grands volumes sans optimisation
Frontièreocsvm

One-Class SVM

Apprend une frontière autour du comportement dominant. Pratique pour des jeux de données petits ou moyens, bien normalisés.

Utile pour
  • chercher une frontière non linéaire
  • tester un autre angle que les arbres ou la densité
  • comparer les candidats instables
Limite
  • sensible à l’échelle des variables
  • peut devenir coûteux sur gros catalogues
Baseline lisiblerobust_zscore

Robust Z-Score

Score transparent basé sur des écarts robustes. C’est le meilleur garde-fou pour voir si les modèles plus complexes racontent n’importe quoi.

Utile pour
  • avoir une mesure simple et explicable
  • contrôler les extrêmes statistiques
  • servir de référence minimale
Limite
  • capte mal les anomalies relationnelles complexes
  • ne suffit pas seul pour une exploration riche
Optionnelpineforest

PineForest

Moteur optionnel basé sur coniferest. Il est prévu comme piste expérimentale pour accélérer certains scorings d’anomalies.

Utile pour
  • tester une variante orientée performance
  • comparer avec Isolation Forest
  • explorer des alternatives modernes
Limite
  • nécessite une dépendance non installée par défaut
  • à garder comme moteur expérimental
Recommandéensemble

Ensemble composite

Combine plusieurs moteurs, normalise leurs scores et peut ajouter une contrainte issue du graphe. C’est le plus cohérent pour du tri exploratoire.

Utile pour
  • réduire la dépendance à un seul modèle
  • croiser score statistique et structure du graphe
  • prioriser les candidats à inspecter
Limite
  • score composite plus difficile à interpréter seul
  • nécessite une documentation claire des poids

Comparaison rapide

La bonne pratique n’est pas de chercher “le meilleur modèle” dans l’absolu, mais de regarder quels candidats reviennent malgré plusieurs lectures différentes.

Modes de features

  • basic : degré, clustering, parallax, mouvements propres, magnitude, distance.
  • extended : ajoute k-core, betweenness, communautés, points d’articulation et ponts.

Pour une page publique ou une démonstration, extended est plus parlant, parce qu’il montre vraiment la dimension “graphe”.

Stratégies de seuil

  • contamination : fraction attendue d’anomalies.
  • percentile : coupe au-dessus d’un percentile.
  • top_k : garde les K meilleurs candidats.
  • score : seuil numérique direct sur anomaly_score.

Pour communiquer clairement, top_k est souvent le plus lisible : “voici les 50 candidats à examiner”.

Commandes utiles

Ces commandes fonctionnent depuis la racine du dépôt après installation des dépendances.

# Installation
pip install -r requirements.txt
# Démo locale, sans réseau
python run_workflow.py --mode csv \
  --in-csv data/sample_gaia_like.csv \
  --out results/demo_ensemble \
  --engine ensemble \
  --threshold-strategy top_k \
  --top-k 50 \
  --plots \
  --explain-top 10
# Comparer plusieurs moteurs sur le même fichier
python run_workflow.py --mode csv --in-csv data/sample_gaia_like.csv --out results/iforest --engine isolation_forest --threshold-strategy top_k --top-k 50
python run_workflow.py --mode csv --in-csv data/sample_gaia_like.csv --out results/lof     --engine lof              --threshold-strategy top_k --top-k 50
python run_workflow.py --mode csv --in-csv data/sample_gaia_like.csv --out results/zscore  --engine robust_zscore    --threshold-strategy top_k --top-k 50
# Ensemble pondéré : on donne plus de poids à la contrainte de graphe
python run_workflow.py --mode csv \
  --in-csv data/sample_gaia_like.csv \
  --out results/ensemble_graph \
  --engine ensemble \
  --ensemble-engines isolation_forest,lof,ocsvm,robust_zscore \
  --ensemble-weights isolation_forest=1,lof=1,ocsvm=1,robust_zscore=.7,graph=1.8 \
  --threshold-strategy top_k \
  --top-k 50

Phrase de prudence à garder visible

Un score d’anomalie n’est pas une découverte astrophysique. C’est un signal de triage : il indique qu’une source mérite une inspection, une comparaison multi-modèles, puis une validation par données externes et expertise métier.
